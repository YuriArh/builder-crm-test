# Спецификация интерфейса: мини-CRM «Объекты и задачи»

Основано на ТЗ и решениях из [DECISIONS.md](./DECISIONS.md). Правила доступа действуют в базе (RLS, права на колонки, функция `change_task_status`). Интерфейс только показывает то, что пользователю реально разрешено, и не служит защитой.

## 1. Роли и термины

| Термин | Значение |
|---|---|
| Постановщик (`manager`) | Создаёт, редактирует и удаляет объекты и задачи, принимает задачи или возвращает их на доработку. Видит всё. |
| Исполнитель (`executor`) | Видит только свои задачи и объекты, где у него есть задачи. Берёт задачу в работу и отправляет её на проверку. |
| Объект | Стройка. Поля: название, адрес. |
| Задача | Поля: название, описание, объект, исполнитель, статус, автор, дата создания. |

### Статусы

| Значение в БД | Подпись | Цвет бейджа |
|---|---|---|
| `new` | Новая | серый |
| `in_progress` | В работе | синий |
| `review` | На проверке | жёлтый |
| `rework` | На доработке | красный |
| `accepted` | Принята | зелёный |

### Действия со статусом (копия правил базы, используется только для показа кнопок)

| Текущий статус | Кнопка | Новый статус | Кто видит кнопку | Комментарий |
|---|---|---|---|---|
| Новая | «Взять в работу» | В работе | назначенный исполнитель | — |
| В работе | «Отправить на проверку» | На проверке | назначенный исполнитель | — |
| На доработке | «Взять в работу» | В работе | назначенный исполнитель | — |
| На проверке | «Принять» | Принята | постановщик | — |
| На проверке | «Вернуть на доработку» | На доработке | постановщик | обязателен |

В остальных случаях кнопок смены статуса нет. Принятая задача окончательная: кнопок смены статуса и кнопки «Редактировать» у неё нет.

## 2. Маршруты

| Адрес | Экран | Доступ |
|---|---|---|
| `/login` | Вход | только гость. Если уже вошёл, перенаправить на `/` |
| `/` | — | перенаправление: постановщика на `/objects`, исполнителя на `/my-tasks` |
| `/objects` | Список объектов | оба |
| `/objects/$objectId` | Карточка объекта со списком задач | оба (исполнитель — только «свои» объекты) |
| `/my-tasks` | Мои задачи | только исполнитель. Постановщика перенаправить на `/objects` |

Search-параметры (через `validateSearch` в TanStack Router):
- `?task=<id>` — открытая модалка задачи. Работает на `/objects/$objectId` и `/my-tasks`. По ссылке можно поделиться задачей, после перезагрузки модалка откроется снова, кнопка «Назад» в браузере её закрывает.
- `?status=<new|in_progress|review|rework|accepted>` — фильтр по статусу. Если параметра нет, показываются все задачи.

Защита маршрутов: в `beforeLoad` проверяется сессия Supabase. Без сессии — переход на `/login` с возвратом на исходный адрес после входа. Профиль текущего пользователя (имя, роль) загружается один раз после входа и кэшируется в TanStack Query.

## 3. Общий каркас (все экраны, кроме входа)

Шапка:
- слева название приложения, по клику открывается `/`;
- навигация: «Объекты» (оба), «Мои задачи» (только исполнитель);
- справа имя пользователя, роль («Постановщик» / «Исполнитель») и кнопка «Выйти».

«Выйти» завершает сессию Supabase, очищает кэш Query и открывает `/login`.

## 4. Экраны

### 4.1. Вход (`/login`)

- Поля «Email» и «Пароль», кнопка «Войти».
- Регистрации и восстановления пароля нет: открытая регистрация отключена по ТЗ.
- Пока идёт запрос, кнопка заблокирована и показывает загрузку.
- При ошибке под формой выводится «Неверный email или пароль». Причину подробнее не раскрываем.
- После входа: если был адрес для возврата, открыть его, иначе `/`.
- Пользователь без профиля в `profiles` (в системе нет роли) видит «Доступ не настроен, обратитесь к администратору», и сессия завершается.

### 4.2. Список объектов (`/objects`)

Таблица или карточки, по каждому объекту:
- название;
- адрес;
- число задач. У исполнителя это число только его задач, так считает RLS.

Клик по объекту открывает `/objects/$objectId`.

**Постановщик:**
- кнопка «Новый объект» открывает модалку с формой «Название», «Адрес». После создания сразу открывается карточка нового объекта: он пустой, и следующий шаг — добавить задачи;
- удаление и редактирование объекта — в его карточке (раздел 4.3), а не в строке списка.
- Удаление требует подтверждения в диалоге: «Объект и все его задачи (N) будут удалены вместе с историей. Действие необратимо». Стандартный `confirm()` браузера не используем.

**Исполнитель:** только просмотр. Видит объекты, где у него есть хотя бы одна задача.

**Пустой список:**
- постановщик видит «Объектов пока нет» и кнопку «Новый объект»;
- исполнитель видит «Вам пока не назначены задачи».

### 4.3. Карточка объекта (`/objects/$objectId`)

Заголовок: название и адрес объекта.

**Постановщик** в заголовке видит «Редактировать объект» и «Удалить объект» (с подтверждением, как в 4.2; после удаления открывается `/objects`).

Список задач объекта, по каждой задаче:
- название;
- бейдж статуса;
- исполнитель;
- дата создания.

Сортировка от новых к старым. Над списком чипы фильтра по статусу: «Все», «Новая», «В работе», «На проверке», «На доработке», «Принята». Фильтр сохраняется в `?status=`.

Клик по задаче открывает модалку (раздел 5) с `?task=<id>`.

**Постановщик:** кнопка «Новая задача» открывает модалку с формой создания (раздел 5.3). Объект в ней уже выбран.

**Исполнитель** видит только свои задачи этого объекта, задачи других исполнителей не показываются.

**Если объекта нет** или он недоступен (RLS вернул пусто): «Объект не найден» и ссылка на список объектов. Мы не различаем «не существует» и «нет доступа».

**Пустой список задач:** «Задач пока нет». Если включён фильтр: «Нет задач в статусе „…“».

### 4.4. Мои задачи (`/my-tasks`, только исполнитель)

Стартовая страница исполнителя после входа.
- Все задачи исполнителя по всем объектам: название, бейдж статуса, объект (ссылка на карточку объекта), дата создания.
- Фильтр по статусу — те же чипы, что в 4.3, в `?status=`.
- Сортировка: сначала задачи, которые ждут действия исполнителя («На доработке», «Новая», «В работе»), затем остальные. Внутри группы — от новых к старым.
- Клик по задаче открывает модалку (раздел 5) с `?task=<id>`.
- Пустой список: «Вам пока не назначены задачи».

## 5. Модалка задачи

Открывается по `?task=<id>` поверх карточки объекта или «Моих задач». Закрывается крестиком, клавишей Esc, кликом по фону или кнопкой «Назад» в браузере. Во всех случаях убирается `?task`.

### 5.1. Режим просмотра (оба)

**Данные:**
- название (заголовок модалки) и бейдж статуса;
- описание (или «Без описания»);
- объект (ссылка на карточку объекта);
- исполнитель;
- автор;
- дата создания.

**Последний комментарий возврата.** Если задача в статусе «На доработке», над действиями выделенным блоком показывается комментарий постановщика из последней записи истории: исполнитель сразу видит, что переделать.

**Действия:** только те, что доступны текущему пользователю в текущем статусе (таблица из раздела 1).
- Исполнитель — кнопки смены статуса.
- Постановщик:
  - «Принять» и «Вернуть на доработку», если задача на проверке;
  - «Редактировать», если задача не принята;
  - «Удалить» в любом статусе (с подтверждением: «Задача будет удалена вместе с историей»).

**История** (оба), лента от старых к новым. В каждой записи:
- дата и время;
- кто сменил статус;
- переход в виде «В работе → На проверке». Стартовая запись: «Задача создана».
- комментарий, если есть.

**Если задачи нет** или нет доступа: «Задача не найдена» в модалке.

### 5.2. Возврат на доработку (постановщик)

Кнопка «Вернуть на доработку» раскрывает в модалке форму с полем «Что нужно исправить» (обязательное, до 2000 символов) и кнопками «Вернуть на доработку» и «Отмена». Пока поле пустое или состоит из пробелов, кнопка отправки неактивна. Обязательность комментария проверяет и база. Если сохранение не удалось, форма остаётся открытой, а текст не теряется.

### Ошибка смены статуса

После любой смены статуса (удачной или нет) задача, её история и списки задач перезапрашиваются. Если база отклонила переход, потому что статус уже изменил кто-то другой, под кнопками показывается «Статус задачи уже изменился, данные обновлены», и кнопки пересчитываются по новому статусу. Остальные ошибки показываются текстом из базы. Оптимистичных обновлений нет: новый статус появляется после ответа базы.

### 5.3. Режим редактирования и создание (постановщик)

«Редактировать» переключает модалку в форму. Создание задачи открывает ту же форму, пустую.

| Поле | Создание | Редактирование | Ограничения |
|---|---|---|---|
| Название | да | да | обязательно, до 200 символов |
| Описание | да | да | необязательно, до 5000 символов |
| Объект | да (заполнен текущим) | да | обязательно, выбор из списка объектов |
| Исполнитель | да | **нет** (только показ) | обязательно, выбор из пользователей с ролью «Исполнитель» |

- Кнопки «Сохранить» и «Отмена». «Отмена» возвращает режим просмотра без изменений.
- Статус, автор и дата создания не редактируются. Новая задача всегда создаётся в статусе «Новая», автор — текущий пользователь.
- При редактировании статус не меняется (решение заказчика).
- Если при редактировании объект изменён, задача переезжает в другой объект. Модалка закрывается, а в карточке текущего объекта задача пропадает из списка.
- Если задачу успели принять, пока постановщик её редактировал, база не сохранит изменения: показываем «Задача уже принята, редактирование недоступно» и перечитываем задачу.

## 6. Поведение данных

- Все запросы идут через `supabase-js` под текущим пользователем, а фильтрацию выполняет RLS. Интерфейс не добавляет своих фильтров «для безопасности».
- Смена статуса выполняется только через `supabase.rpc('change_task_status', { p_task_id, p_new_status, p_comment })`.
- После любого изменения перезапрашиваются затронутые данные (инвалидация в TanStack Query):
  - объект → список объектов и карточка объекта;
  - задача → список задач объекта, «Мои задачи», модалка задачи и её история, число задач в списке объектов.
- Пока идёт сохранение, кнопки действия заблокированы: повторный клик не отправит запрос дважды.
- Ошибки показываются в модалке рядом с действием. Сообщения функции `change_task_status` написаны по-русски, в том числе с русскими подписями статусов.
- Ограничения длины полей в формах совпадают с ограничениями в базе.
- Фильтр по статусу применяется на клиенте к уже загруженному списку: переключение чипов не делает новых запросов.
- Даты показываются в формате `06.11.2026 14:30` в часовом поясе браузера.

### Ключи запросов (TanStack Query)

| Ключ | Данные |
|---|---|
| `['me', userId]` | профиль текущего пользователя (userId в ключе — кэш не путается при смене пользователя) |
| `['objects']` | список объектов с числом задач |
| `['objects', id]` | объект |
| `['tasks', { objectId }]` | задачи объекта |
| `['tasks', 'mine', userId]` | задачи текущего исполнителя |
| `['tasks', id]` | задача с объектом, исполнителем и автором |
| `['tasks', id, 'history']` | история задачи |
| `['executors']` | исполнители для формы задачи (только постановщик) |

## 7. Не входит в эту версию

- Переназначение исполнителя (обсудить на созвоне, см. DECISIONS.md).
- Поиск по названию, пагинация. При объёме тестового задания списки небольшие.
- Обновление в реальном времени: изменения другого пользователя видны после перезагрузки данных (повторный запрос при возврате на вкладку делает TanStack Query).
- Отдельная мобильная вёрстка. Интерфейс должен оставаться пригодным на узком экране, но отдельно не оптимизируется.
- Управление пользователями и ролями из интерфейса: только через Supabase Dashboard.
