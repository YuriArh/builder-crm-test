# Решения и допущения

Здесь записано, что решено там, где ТЗ не даёт однозначного ответа, и чего нет в этой версии.

Обозначения:
- **[Решено]** — решение принято, его нужно реализовать.
- **[Решено, заказчик]** — ответ заказчика на уточняющий вопрос.
- **[Допущение]** — вариант по умолчанию, пока нет ответа заказчика.
- **[Открыто]** — вопрос задан или ещё будет задан заказчику.

## Задачи

- **[Решено] Исполнитель назначается при создании задачи и не меняется.** В ТЗ переназначение не требуется. Запрет действует на уровне базы: у клиента нет права UPDATE на колонку `assignee_id`.
- **[Решено, заказчик] Задачу можно редактировать, пока она не принята. При редактировании статус не меняется.** Постановщик меняет название, описание и объект в статусах «Новая», «В работе», «На проверке» и «На доработке». Принятую задачу редактировать нельзя: правило RLS на UPDATE пропускает только задачи со статусом не `accepted`.
- **[Решено, заказчик] Постановщики могут редактировать, принимать, возвращать и удалять задачи друг друга.** Права есть у любого постановщика, а не только у автора задачи.
- **[Решено, заказчик] При удалении задачи её история удаляется вместе с ней** (каскадное удаление). Запрет на удаление истории через API от этого не страдает: удалить отдельную запись истории нельзя, она исчезает только вместе с задачей.
- **[Допущение]** Задачу можно удалить в любом статусе, в том числе после «Принята»: заказчик ограничил только редактирование.
- **[Допущение]** Если два постановщика одновременно редактируют одну задачу, сохраняются изменения того, кто сохранил последним. Защиты от одновременного редактирования нет. Одновременные смены статуса защищены: функция смены статуса блокирует строку задачи, поэтому второй переход проверяется уже от нового статуса.
- **[Допущение]** Поля `author_id`, `created_at` и `status` нельзя изменить обычным редактированием: у клиента нет прав на эти колонки. Статус меняется только через функцию `change_task_status`, которая проверяет переход по таблице из ТЗ.
- **[Допущение]** «Принята» — окончательный статус. Переходов из него в ТЗ нет.
- **[Допущение]** Комментарий обязателен при переходе «На проверке → На доработке». При остальных переходах его можно не писать.
- **[Допущение]** Постановщик не может выполнять переходы исполнителя от его имени, например брать задачу в работу.

## Объекты

- **[Решено] Объект удаляется вместе со всеми его задачами и их историей** (каскадное удаление).
- **[Допущение]** Исполнитель видит объект, если в нём есть хотя бы одна его задача в любом статусе. В карточке объекта он видит только свои задачи.

## История статусов

- **[Допущение]** При создании задачи в историю пишется стартовая запись «— → Новая».
- **[Допущение]** Записи истории создаёт только база: стартовую запись — триггер при создании задачи, остальные — функция `change_task_status`. У клиента нет прав INSERT, UPDATE и DELETE на таблицу истории.
- **[Допущение]** В историю пишутся только смены статуса. Правки названия, описания и других полей не пишутся.

## Роли и пользователи

- **[Допущение]** У пользователя одна роль. Роль хранится в `profiles`, менять её может только администратор через Supabase. Пользователь не может изменить свою роль сам.
- **[Допущение]** Открытая регистрация отключена, тестовые пользователи создаются вручную в Supabase.
- **[Допущение]** Исполнитель видит свой профиль и профили всех постановщиков: это нужно, чтобы показать автора задачи и того, кто менял статус. Других исполнителей он не видит. Постановщик видит всех, потому что выбирает исполнителя.

## Обсудить на созвоне

### Переназначение исполнителя

Сейчас исполнитель задаётся при создании задачи и потом не меняется (см. раздел «Задачи»). Если переназначение понадобится, возможны два варианта.

**Вариант 1. Переназначать можно только в статусе «Новая». Оценка: 10–15 минут.**
- Триггер разрешает менять `assignee_id`, только пока статус «Новая».
- RLS не меняется: правила доступа завязаны на `assignee_id`, поэтому доступ сам переходит к новому исполнителю.
- В интерфейсе: выпадающий список исполнителей в форме редактирования.
- История не меняется, потому что статус остаётся прежним.

**Вариант 2. Переназначать можно в любом статусе. Оценка: 30–60 минут.** Большая часть времени уходит на согласование правил, а не на код:
- **Что делать со статусом:** сбрасывать задачу «В работе» в «Новая», чтобы новый исполнитель сам её взял, или оставлять как есть. От этого зависит логика триггера.
- **История:** сейчас в ней только смены статуса. Чтобы записывать и переназначения, нужен тип события или поля «старый / новый исполнитель», а затем доработка триггера и отображения истории.
- **Доступ:** старый исполнитель сразу теряет задачу, а если других задач на объекте у него нет, то и сам объект. RLS это обеспечивает, но такой случай нужно проверить.
- **Проверки:** исполнитель не должен переназначить задачу ни себе, ни другому через API. Это ещё одна проверка в триггере.

Вопросы к заказчику: нужно ли переназначение, в каких статусах и нужно ли записывать его в историю.
